Meshtastic vs. MeshCore: how airtime is calculated

Similar radio physics. Different counters, time windows, and definitions of a busy channel.

Code review · October 26, 2026

Meshtastic’s “Air Util TX” and MeshCore’s TX airtime measure the same general thing—this node’s transmissions—but use different accounting and time windows. Meshtastic’s “Channel Utilization” has no exact MeshCore equivalent.

This comparison follows the public firmware and client code. The firmware snapshots reviewed are Meshtastic eaba8b95 and MeshCore 81dbae59; installed releases can differ. MeshCore’s official native mobile app is closed source, so its firmware inputs can be verified, but not every calculation in its UI.

How they calculate packet airtime

Both use RadioLib’s LoRa time-on-air calculations. These account for spreading factor, bandwidth, coding rate, preamble, header/CRC settings, and the complete radio packet length. They include preamble and coding overhead—not just the user’s message bytes.

Meshtastic’s computePacketTime() calls getTimeOnAir() or calculateTimeOnAir() and converts microseconds to integer milliseconds. For received packets, supported drivers can incorporate the received header’s coding rate and CRC flag. MeshCore’s normal getEstAirtimeFor() calls getTimeOnAir(len_bytes) / 1000, using the configured radio settings.

Source: Meshtastic calculation · MeshCore calculation

Matching SF/BW/CR alone is insufficient. For example, the inspected Meshtastic code normally uses a 16-symbol sub-GHz preamble; MeshCore uses 32 symbols at SF8 and below, otherwise 16. Packet formats and lengths also differ. Thus, equal-length chat messages need not have equal airtime.

Source: Meshtastic preamble · MeshCore preamble

How they account for actual traffic

Meshtastic: modeled duration, rolling percentages

Meshtastic records the calculated packet duration after a successful transmission. Its firmware then produces:

air_util_tx = 100 × TX milliseconds in retained buckets / 3,600,000

channel_utilization =
  100 × (TX + good RX + bad RX) milliseconds in retained buckets / 60,000

TX uses sixty one-minute buckets; channel utilization uses six ten-second buckets. These are bucketed rolling windows, rather than exact sliding windows. The denominators remain a full hour/minute even immediately after boot. The firmware sends these percentages directly in telemetry.

Source: TX/RX logging · Window calculations · Telemetry assignment

MeshCore: cumulative TX and RX counters

MeshCore treats TX and RX differently:

  • TX: adds elapsed milliseconds between starting a send and observing successful completion. This can include driver/setup and loop-observation overhead, so it is not quite the same as calculated RF duration.
  • RX: adds the estimated packet airtime only after the radio read and MeshCore packet parsing succeed. Failed reads/CRC errors and packets rejected by that parser do not contribute.
  • Both accumulate as counters, exposed as whole seconds. Repeater status’s misleadingly named total_air_time_secs is TX only; total_rx_air_time_secs is separate.

Source: Dispatcher implementation · Repeater status serialization

Consequently, Meshtastic includes more failed-reception activity in channel utilization. Neither metric measures all RF energy or all interference on the frequency: this is packet accounting, not a spectrum-analyzer occupancy measurement.

What the apps display matters

Meshtastic clients generally display the already-calculated firmware percentages. For example, its web client formats airUtilTx and channelUtilization as percentages.

Source: Meshtastic web client formatting

A MeshCore client can derive a percentage differently. One concrete public example, Colorado-Mesh’s mesh-client, calculates:

Airtime % = 100 × totalAirTimeSecs / totalUpTimeSecs

That is average TX utilization since boot, not TX utilization during the last hour, and not TX+RX channel utilization. This is verified for that client, not an assertion about the closed-source official app.

Source: Client calculation

How to make equivalent comparisons

Take two MeshCore counter readings separated by a known interval. Here, Δ means the change between those readings:

TX utilization % = 100 × ΔTX_seconds / Δelapsed_seconds
RX utilization % = 100 × ΔRX_seconds / Δelapsed_seconds
TX+RX %           = 100 × (ΔTX_seconds + ΔRX_seconds) / Δelapsed_seconds

Use one hour of TX counter change to approximate Meshtastic’s air_util_tx. Differences remain from Meshtastic’s bucket boundaries and modeled TX duration versus MeshCore’s elapsed TX timing.

Worked example

36 additional TX seconds ÷ 3,600 elapsed seconds × 100 = 1% TX utilization.

This compares the last hour of transmissions. Dividing the lifetime counter by uptime would answer a different question.

Use one minute of TX+RX counter change for the closest MeshCore approximation to Meshtastic’s channel utilization—but label it successful-packet TX+RX utilization, because it lacks Meshtastic’s failed/malformed RX contribution. Account for counter wrap/reboots, and expect coarse results over short intervals because the exported counters have whole-second precision.

Airtime factor is a limit, not a measurement

MeshCore’s airtime factor is not an observed percentage. The inspected code derives an allowed fraction as 1 / (1 + factor) and uses it to replenish a TX budget: factor 1 corresponds to 50%, factor 9 to 10%. That describes permission to transmit, not how busy the node or channel actually was.
